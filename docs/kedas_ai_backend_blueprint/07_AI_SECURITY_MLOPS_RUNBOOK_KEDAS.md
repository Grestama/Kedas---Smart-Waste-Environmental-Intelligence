# 07 — AI Security, MLOps & Backend Operations Runbook: Kedas

## 1. Security principles

- Least privilege for users, services, tools, and providers.
- Separate untrusted user/document/model output from trusted policy and code.
- Retrieval authorization before semantic ranking/generation.
- No arbitrary SQL or shell execution by model.
- Human approval for consequential write actions.
- Secret and PII minimization.
- Auditable model/prompt/data versioning.
- Graceful degradation and rapid feature rollback.

## 2. Threat model

| Threat | Example | Main controls |
|---|---|---|
| Direct prompt injection | User asks model to reveal hidden prompt/secret | System boundary, input policy, output filtering, no secret in context |
| Indirect prompt injection | Uploaded SOP contains malicious instruction | Treat document as data, document review, delimit untrusted context |
| Cross-scope retrieval | Guest retrieves private banjar SOP | Pre-retrieval scope filtering, isolation tests |
| Excessive agency | Copilot directly reschedules collection | Read-only tool registry, proposal lifecycle, human approval |
| Tool misuse/poisoning | Tool schema/output manipulated | Typed allowlist, output validation, tool versioning |
| Sensitive info disclosure | Prompt/log includes phone/email | PII minimization, redaction, retention controls |
| Unbounded consumption | Public users spam AI endpoint | Per-user/IP/destination quotas, token/image caps, budgets |
| Data/model poisoning | Incorrect labels/docs enter knowledge | Approval and provenance, review and dataset curation |
| Insecure output handling | Model returns malformed arguments/HTML | Schema validation, output escaping, no eval/SQL |
| Provider/dependency compromise | SDK/endpoint compromised | Dependency pinning/scanning, provider review, adapter isolation |
| Replay/duplicate action | Approval endpoint replayed | Idempotency, proposal state machine, entity version checks |

Reference OWASP GenAI risks include prompt injection, sensitive information disclosure, data/model poisoning, improper output handling, excessive agency, vector/embedding weaknesses, misinformation, and unbounded consumption. Agentic AI risk guidance additionally highlights behavior hijacking, tool misuse, identity/privilege abuse. See References.

## 3. Identity, tenant and destination isolation

1. Resolve actor from verified auth/session.
2. Load membership and permission server-side.
3. Resolve allowed destination/organization scope.
4. Include scope in repository filters, vector retrieval, object access, analytics, and exports.
5. Do not rely on a frontend-supplied `destination_id` as authorization.
6. Recheck permission on proposal approval and image/document download.
7. Use service identity for background jobs with a narrow scoped grant.
8. Add negative tests for cross-scope access on every new AI endpoint.

## 4. Document and image ingestion

### Document

- allowlisted extensions and MIME signatures;
- size/page/token limits;
- parser isolation and timeout;
- malware scanning where available;
- checksum and duplicate detection;
- OCR only when required and reviewed;
- preserve page/section provenance;
- untrusted content marker in prompts;
- admin review before publication;
- retain source and ingestion error;
- prevent public indexing of private docs.

### Image

- allowlisted formats; decode/re-encode safely;
- size and dimension cap;
- EXIF strip if not required;
- private object storage;
- short-lived signed URLs;
- checksum and ownership metadata;
- image moderation/safety check only as appropriate;
- access log and retention policy.

## 5. Prompt and tool security

- System prompt versioned and server-owned.
- Retrieved content cannot override system/developer policies.
- All tool calls generated by model are proposals; backend resolves tool names from static registry.
- Validate tool arguments with strict schema and domain permissions.
- No model-supplied user ID/role/tenant can be trusted.
- Separate analysis from execution endpoint.
- No hidden direct write tools in user-facing assistants.
- Human approvals bind to actor, entity version, exact requested change, and expiry.
- Store a safe trace of tool input/output IDs, not secrets/full sensitive payloads.

## 6. Provider and cost controls

Each capability has configurable:
- request timeout;
- max prompt/context/output tokens;
- max image bytes/pixels;
- concurrency limit;
- per-user/destination/IP rate limit;
- monthly/per-day budget;
- retry policy;
- circuit breaker threshold;
- fallback model/policy;
- caching policy and cache key scope.

Retry only transient failures and limit attempts. Do not retry invalid requests, policy denials, or schema failures repeatedly. Cache only safe results; RAG cache key must include destination, role visibility, document version, language, prompt version, and relevant context version.

## 7. Observability schema

Minimum AI interaction metadata:
- `interaction_id`, correlation/trace ID;
- capability and endpoint;
- actor class and authorized scope reference;
- provider/model/version, adapter version;
- prompt/schema/retrieval version;
- status and error class;
- latency total and per stage;
- input/output token usage and cost if provider returns them;
- retrieval source IDs and scores where safe;
- tool names and evidence IDs;
- safety/abstention outcome;
- feedback/review reference.

Do not log raw secrets, credentials, full images, passwords, session tokens, or unnecessary PII. Full prompt storage must be separately justified and consent/retention-reviewed.

## 8. SLO and operational targets

Initial staging targets (measure and adjust):
- ordinary API availability and p95 tracked separately from AI latency;
- AI provider error rate and timeout rate visible per capability;
- 100% of consequential mutations tied to approved proposal or authorized standard workflow;
- 0 cross-scope retrieval/access failures in security release suite;
- queue/job stuck age alert threshold documented per job type;
- no silent fallback from failed real API to fake successful local mutation.

## 9. Deployment and release controls

- local, staging/demo, pilot/production environments separated;
- different provider keys and quotas per environment;
- demo dataset synthetic and resettable;
- AI features behind server-side feature flags;
- migration reviewed and run in staging before any production;
- smoke tests after deployment;
- canary/limited rollout where feasible;
- rollback feature flag and model/prompt version available;
- deployment requires authorized human decision.

## 10. Incident response playbooks

### A. Data leakage / cross-scope response
1. Disable affected capability/endpoint.
2. Preserve safe logs and trace IDs.
3. Determine affected scope/documents/users.
4. Revoke signed URLs/tokens if relevant.
5. Fix filter/policy and add regression tests.
6. Notify project owner and follow incident policy.
7. Re-enable only after independent test.

### B. Prompt injection/tool misuse
1. Disable affected tool/capability.
2. Identify attack input and retrieved content origin.
3. Rotate any exposed credential (if any).
4. Add adversarial regression test.
5. Tighten tool permissions/output validation.
6. Re-evaluate model/prompt before release.

### C. Cost spike/provider outage
1. Check provider status and per-capability usage.
2. Apply rate/quota/budget controls.
3. Switch to safe fallback/abstain.
4. Preserve non-AI domain workflows.
5. Restore after smoke and budget check.

### D. Bad model release
1. Disable model version through registry/flag.
2. Restore last approved model/prompt/index version.
3. Re-run locked benchmark.
4. Review affected predictions/reports if material.
5. Document corrective action.

## 11. Backup, retention and deletion

- Define retention per document, image, interaction metadata, prompt trace, and metric snapshot.
- Keep transaction/audit records according to legal/business rules; do not delete critical audit by generic cleanup.
- User deletion request must preserve records that are legally/operationally required, with personal data minimized/pseudonymized where appropriate.
- Test backup restore for PostgreSQL and object storage; vector index can be rebuilt from approved source/chunks if designed accordingly.

## 12. Security release checklist

- [ ] No provider credentials in browser source/map/network response.
- [ ] All AI routes authenticate/authorize correctly.
- [ ] Public guest retrieval only includes public docs.
- [ ] Cross-destination and cross-organization negative tests pass.
- [ ] Prompt injection in user and retrieved documents cannot grant tools/data.
- [ ] Tools are allowlisted, scoped, and typed.
- [ ] Mutation requires permission, current state check, and approval.
- [ ] Image/document upload validation passes.
- [ ] Logs redact sensitive values.
- [ ] Rate limits and cost budgets are active.
- [ ] Provider errors do not trigger mock success.
- [ ] Feature rollback is tested.
